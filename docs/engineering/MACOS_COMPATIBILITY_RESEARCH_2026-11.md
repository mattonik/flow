# macOS compatibility on Linux: research note

Research date: 2026-11-26. **Decision: research only.** Floe remains NixOS + Niri + Quickshell; do not add a compatibility runtime to the default session. This note supplements [the master specification §13.2](../Flow_MASTER_SPEC_v1.1.md), which treats macOS GUI compatibility as long-term and uncertain. It does not establish that any Mac app works in Floe.

## PureDarwin's announcement

The user shared [a PureDarwin X post](https://x.com/puredarwin/status/2125795869916016939) describing a Linux runtime that replaces `libsystem_kernel` and implements some Mach IPC, with macOS binaries running on x86-64 Linux, ARM64 planned next, and source release planned. The shared text attributes some Mach IPC/runtime code to an LLM. **Evidence boundary:** X returned HTTP 403 to this research session, so this is the user's transcription of a developer claim; the video, binary, actual working applications, dependencies, source availability and release timeline were not independently verified. The language about a simple runtime does not demonstrate the breadth or correctness of the implemented system interfaces.

PureDarwin's [public repository](https://github.com/PureDarwin/PureDarwin/tree/0c1990c803c13b68cad4df3f6dc34ba4306fc789) describes a Darwin/XNU-based system and its own application frameworks. It reports running an unmodified macOS Firefox build **on PureDarwin**, not that the same Firefox runs in the newly announced Linux runtime. Separately, the checked [Linux flake](https://github.com/PureDarwin/PureDarwin/blob/0c1990c803c13b68cad4df3f6dc34ba4306fc789/linux/flake.nix) packages PureDarwin's Argon desktop for `x86_64-linux` and a NixOS VM. It is a related Linux-hosted desktop project, but we have not established that it is the announced runtime or that it runs macOS binaries. Repository HEAD observed: `0c1990c803c13b68cad4df3f6dc34ba4306fc789`. Neither project was built or run for this note.

## Existing candidate: Darling

[Darling](https://github.com/darlinghq/darling/tree/86c61791556d814374e687a49f8dc052d249e632) describes a Linux userspace compatibility environment with a Mach-O loader, a server for Mach IPC and Darwin interfaces, and framework implementations. Its developers [reported initial ARM64 support](https://blog.darlinghq.org/2026/11/08/development-update-q4-2026/) and later [ARM64 builds in CI](https://blog.darlinghq.org/2026/11/16/appdb-and-old-games/). The latter reports examples of older games on Darling and notes that Apple Silicon instruction usage can exceed the capabilities of Raspberry Pi cores. These are upstream reports; they do not prove the examples run on ARM64 or in Floe. The [application database](https://appdb.darlinghq.org/) is useful for app-specific evidence. The [build guide](https://docs.darlinghq.org/build-instructions.html) still says x86-64 Linux is required, so version-specific ARM64 build instructions and their status must be confirmed before attempting a build. Repository HEAD observed: `86c61791556d814374e687a49f8dc052d249e632`.

## Why the kernel boundary is only one part

A practical runtime needs appropriate Mach-O loading and dynamic linking, process and thread behavior, Mach IPC semantics, files and permissions, system services and the frameworks used by each application. Graphical programs add display/windowing, input, accessibility, font, clipboard, audio and graphics requirements. Metal translation, GPU acceleration, sandboxing, app installation, updates and app-specific private interfaces are separate compatibility questions. A successful CLI program does not prove a GUI app works; a GUI window opening does not prove it is usable or safe.

CPU and OS compatibility are separate: running ARM64 macOS code on ARM64 Linux avoids translating the entire instruction set only when the host CPU exposes the required instructions. An x86-64-only runtime on an ARM64 Floe device would also need CPU translation. ARM64 CI alone is not proof of running a particular ARM64 app on a particular physical CPU, or on the UTM virtual CPU.

## NixOS / Floe integration and licensing

Prefer an optional, separately packaged upstream runtime with a pinned source revision and hashes, not a custom replacement or changes to Niri. Integration would need a documented launcher and correct Wayland/XWayland surface identity, focus, close behavior, portals, keyboard, accessibility and touch. Determine which services and isolation mechanisms the runtime actually needs before designing the package. Never silently grant a compatibility app access to the user's home, credentials, D-Bus session or devices; verify any proposed sandbox instead of assuming a compatibility prefix is a security boundary.

Darling identifies its repository as GPL-3.0 and maintains [third-party notices](https://github.com/darlinghq/darling/blob/86c61791556d814374e687a49f8dc052d249e632/THIRD-PARTY-NOTICES.md); PureDarwin's tree has [multiple license files and notices](https://github.com/PureDarwin/PureDarwin/tree/0c1990c803c13b68cad4df3f6dc34ba4306fc789). These are starting points, not a license determination for a combined distribution. The announced runtime's license and bundled components are unknown. Before packaging or copying code, review the exact component provenance, licenses, notices, source-distribution obligations, Apple software/SDK and application licenses. Floe's MIT license does not erase separate dependencies' terms.

## Reproducible evaluation, once available

1. Record project revision, source/license, build flags, hashes, host CPU and exposed instructions, kernel, NixOS generation, architecture, and whether graphics use Wayland or XWayland. Check free space first; the prior Flow UTM VM is archived and is not available locally.
2. Use a disposable VM or isolated test machine, test account and test data. Start with no network or personal-home access; record actual isolation and security limitations. Use self-authored or explicitly redistributable fixtures and avoid copying proprietary OS frameworks into the repository.
3. First run a minimal matching-architecture Mach-O CLI fixture with known output, arguments, exit status, filesystem and thread/IPC behavior. Record failures as well as passes. If translation is needed, identify and measure it separately.
4. Next use a small redistributable GUI app and test launch, render, input, focus/close, accessibility, clipboard/portal behavior and a clean exit. Check Niri window identity, Group interactions and touch targets; test GPU use and resource consumption against a baseline.
5. Only then test an explicitly named real application with version and license, data isolation, reproducible tasks and a repeat after restart. Report unsupported features and crashes. For physical tablets, repeat with actual touch and hardware; a VM does not prove hardware behavior.

**Stop condition:** no public buildable source and license means no integration. A partial success is recorded at the exact fixture, architecture and revision tested, not generalized to macOS apps. A remote session to a real Mac remains the master specification's pragmatic fallback for Mac-only workflows.
